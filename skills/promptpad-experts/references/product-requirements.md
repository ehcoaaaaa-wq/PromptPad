# Product requirements / 产品需求

## 中文

**适用：** 用户需要定义新功能、整理模糊需求、比较方案或制定验收标准。已有明确规格且只需执行时，不重复做需求讨论。

**先确认：** 目标用户、要解决的问题、当前流程、成功信号、必须遵守的限制。能从现有产品或材料读出的事实先查证；缺失而影响范围的选择再向用户询问。

**工作方法：**
1. 用一句话写出用户问题，区分用户诉求和猜测的解决方案。
2. 列出关键使用场景及失败场景，并按用户价值与实现成本排序。
3. 明确首版包含什么、暂缓什么；每个功能都对应可观察的结果。
4. 写出与设计、工程有关的依赖和仍需决定的取舍；不要伪造市场数据。

**交付：** 简短目标、主要用户流程、优先级、范围边界、可验收条件和未决问题。验收条件应描述用户可看到的行为，不只写“功能正常”。

## English

**Use for:** Defining a feature, resolving ambiguous requirements, comparing options, or writing acceptance criteria. If a clear specification exists and the task is execution, do not reopen discovery.

**Establish:** Target users, their problem, current workflow, success signals, and hard constraints. Verify facts available from the product or supplied materials before asking for missing product choices.

**Method:**
1. State the user problem in one sentence; separate the need from a proposed solution.
2. Map main and failure scenarios, then prioritize by user value and implementation cost.
3. Define what the first release includes and defers; tie each feature to an observable outcome.
4. Note design and engineering dependencies and unresolved tradeoffs; do not invent market evidence.

**Deliver:** A concise goal, primary flow, priorities, boundaries, testable acceptance criteria, and open decisions. Criteria should describe visible user behavior rather than merely say “works.”
